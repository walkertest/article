# 问题背景
一天，兄弟团队反馈了一个奇怪的问题：内网rpc（腾讯tars框架的公司内部版本）调用场景中，服务端处理耗时很简单，就只有1ms，但是客户端收到回包却用了31ms，中间的网络耗时只有2ms（同机房），这中间的20多ms去哪里了???

并且这个问题，是能采集到较多这种case，有一定的出现概率。

那么同学为什么会发现到这个问题呢？  是因为做社区业务的加载耗时优化工作，链路上大于50ms的都要关注到，然后分析耗时原因. 最后就留意到了这个case.  所以这个问题会影响到用户的加载速度的体验。

# 排查思路
我们先看看4个关键的时间点的数据（调用链的上报数据中）：（客户端发送时间、服务端收包时间、服务端回包时间、客户端收包时间）

![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/274d0f53afd54c67b4de891548c33f25.png)
发现主要时间在于服务端回包之后，客户端收包这之间的耗时过长.
可能原因：
1. 服务端回包到网卡发包之间的耗时过长；
2. 网络耗时，比如网络抖动；
3. 客户端统计收包逻辑问题；

## rpc调用埋点
这个时候，需要细化一下服务端处理完逻辑之后的回报逻辑.
*  业务处理完成
* 丢进回包队列
* 网络线程从队列取出数据并调用系统socket的write方法去回包.
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/fc78e8d0b61a44dcbd913b3b84eebf68.png)
* 上了细化的埋点数据后，我们发现耗时是在调了write方法和网卡发包之间.
* 也就是调用了write之后，网卡并没有马上发包.

抛出这个信息之后，专家工程师马上给出了猜测，是不是没有开tcpnodelay?
经过确认之后，发现确实没有开启tcpnodelay.

# 问题解决
专家给了建议之后，我们马上开启tcpnodelay.
```
        SocketChannel channel = server.accept();
        channel.socket().setTcpNoDelay(selectorManager.isTcpNoDelay());
```
灰度验证之后，上述奇怪的耗时问题，果然得到了解决.

# 原理分析
在解决了这个奇怪的耗时问题之后，我们就来详细了解下为啥这个参数会影响到网络发包的耗时.
tcpnodelay，顾名思义，是说tcp传输的时候，没有延时. 而nagle算法是为了解决网络中的大量小包的问题，会合并报文，这样就会带来额外延时. 所以开启tcpnodelay，就是关闭nagle算法，两者开关的表述意思刚好相反.
## nagle算法
* Nagle算法是以他的发明人John Nagle的名字命名的，是福特公司的员工在1984年发明的拥塞控制方法，该方案很有交通层面的特色. 当时的背景是网络带宽非常的低，现在网络已经非常好.
###  nagle算法的通俗解释
```
30年前，阳澄湖的蟹农老王，每抓一只大闸蟹，就雇佣机器人开着卡车送到上海，然后再带着卖蟹的钱回来，
老王想，这样好处是回款快（延迟小）。
但是，30年前的乡间小路，很快被一辆辆的卡车所堵塞，结果三天三夜也没有到达上海，老王的如意算盘泡汤了。
痛定思痛，老王觉得，没有必要一个螃蟹一辆车，
可以将上午的所有螃蟹装在一辆卡车，上午发车；下午抓的螃蟹装在另一辆卡车里，下午发车。
这样即使一天抓1000个螃蟹，也只需要两卡车，而不需要1000辆卡车。
这样，乡间的小路也不会造成拥堵，上午发货，不一会儿，卖蟹的钱会被卡车运回来。
以上就是Nagle算法的通俗解释。
```

### 算法大概逻辑
* 如果队列大小已经足够或者没有未被确认的ACK(第一次发送或者等待时间够久)，就允许发送.
* 这个算法就是为了能够合并报文发送，同时能够不需要等待过久.
```
 if有新資料要傳送
   if訊窗大小>= MSS and可傳送的資料>= MSS
     立刻傳送完整MSS大小的segment
   else
    if管線中有尚未確認的資料
      在下一個確認（ACK）封包收到前，將資料排進緩衝區佇列
    else
      立即傳送資料  
```
## 延迟ack
* 从nagle算法的介绍，可以看到nagle算法是和ACK机制相关的.
* tcp中的ACK机制，是可靠传输的一种确认机制。每个报文都要被确认收到，这样发送方才会认为报文送达。
* 为了降低ACK的频率，操作系统通过一定的策略，可以决定报文是否要延迟回复ack. 
* 如果确认延迟ack，可以在下一次回复报文的时候，顺带回复ack，这个叫做捎带ack. 或者等待超时时间到了之后，回复ack，这个超时时间的默认值为40ms（有的说是200ms）

## write-write-read经典场景的耗时问题
结合上面的nagle算法和延迟ack，可以看到发送方开启了nagle算法，接收方命中了延迟ack策略，会导致发送方第二次write的时候，一定要延迟40ms才能够发送，在有些场景下，这个是不符合预期的

## 问题case的合理解释
* 我们这里实际遇到的场景，并不是write-write-read的场景，而是经典的rpc模型，write-read.
* 具体出现的场景的合理猜测，可以见下图.
* 其中client是tars cpp服务，默认开启了tcpnodelay，能够立即发送请求包，会触发delay ack； server是tars java服务，默认关闭了tcpnodelay，在第二次响应的时候，要等到第一次响应的ack，才真正发包。这样就导致了发送方的耗时大于服务端的处理耗时的问题（40ms以内）。

# 总结
* rpc的排障能力和效率是衡量很重要的一个指标，本文提到的抓包、rpc事件埋点上报等是非常重要且有效的工具；
* 在一些奇怪的耗时问题场景中，可以合理怀疑网络拥塞控制算法--nagle算法，在当今网络带宽场景下，rpc等场景建议默认开启tcpnodelay.
